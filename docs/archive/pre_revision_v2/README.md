# Let's Move Stars! — A Guide to the Experiment

## What is this project?

This is a desktop experiment about how people imagine a smooth curve through a set of dots. It runs in Python using Pygame. There is no website.

Imagine seeing a row of stars that suggests a curved path. One star is out of place. Your task is to move that star to where you think the path should go.

The experiment asks: **Which nearby dots influence your choice, and does that influence change when the shape bends differently?**

## What does a participant do?

Each trial shows **eight fixed white dots and one movable white dot** inside a dark circular area. The connecting curve is not drawn. Two green markers show the line along which the movable dot can travel.

1. Look at the shape suggested by the fixed dots.
2. Move the adjustable dot until it seems to fit a smooth continuation of that shape.
3. Press Enter or Space, or click Next, to submit the setting.
4. The program saves the trial to both CSV files before starting the next trial.

The session begins with instructions and an unrecorded practice trial.

### Controls

| Control | What it does |
|---|---|
| Z or Up arrow | Moves toward the green marker labeled Z |
| / or Down arrow | Moves toward the green marker labeled / |
| 1 | Selects a fine step: 1 pixel |
| 2 | Selects a medium step: 5 pixels |
| 3 | Selects a coarse step: 10 pixels |
| Enter, Space, or Next | Submits the current setting |
| Esc or closing the window | Exits; already completed trials remain saved |

Changing movement direction automatically reduces the step size, down to 1 pixel. Selecting 1, 2, or 3 restarts this step-size rule. Because the shape can be tilted, “Up” does not necessarily mean toward the top of the screen; follow the marker labels.

## How are the dot patterns made?

A **stimulus** is simply the visual pattern shown to a participant. The program makes each pattern in five steps.

### 1. Start with a simple curve

The default curve families are:

| Name in the data | Starting curve | Plain-language description |
|---|---|---|
| `line` | `y = 0` | A straight line; equivalent in shape to a rotated `y = x` |
| `parabola` | `y = 0.75 × x²` | A bowl-shaped curve |
| `cubic` | `y = 0.80 × x³` | An S-shaped curve |
| `quartic` | `y = 0.90 × x⁴` | A bowl with a flatter middle and steeper sides |
| `quintic` | `y = x⁵` | An S-shape with a flatter middle and sharper outer bending |
| `circle` | Half of a circle | A curve with constant bending |

The polynomial curves start with x between −1 and +1. These equations describe the shape **before** it is resized, reflected, and tilted for display. Optional strength settings can change the polynomial coefficients.

Although the project discusses “visual splines,” these stimuli are sampled from individual polynomial curves or a semicircle. They are not generated by fitting a spline through the participant's response. A stimulus's degree does not tell us which interpolation rule a participant uses.

### 2. Pick nine positions along the curve

Points are selected by distance **along the curve**, rather than by equal steps across the screen. The default positions are at:

`0%, 11%, 23%, 35%, 50%, 65%, 77%, 89%, 100%`

The spacing is deliberately slightly uneven. Points are numbered **0 through 8** in their original order along the curve. Reflection and rotation do not change these labels.

The program aligns and uniformly resizes each curve so that its two endpoints have a common separation in the internal coordinate system. It can reflect the shape and rotate it between −22.5° and +22.5°. Display scaling also reserves room for the planned displacements.

### 3. Replace one point with the adjustable dot

The original position of this point is hidden. Instead, participants see a movable dot starting approximately 70 pixels to one side of it. Starting sides are balanced across the full default design. The starting offset is shortened if necessary to stay inside the allowed area.

The dot moves along a line approximately perpendicular to the original curve at the hidden point. This perpendicular direction is called the **normal**. It is estimated from neighboring baseline points.

The default experiment uses two hidden locations: point 3, which is off-center, and point 4, which is halfway along the curve.

### 4. Slightly displace selected fixed dots

On some trials, the program shifts one or two fixed dots away from their original positions. This deliberate shift is called a **perturbation**. Those dots stay fixed while the participant responds.

Each shift follows the normal at that dot. In the default experiment, its size is **4% of the dot's local spacing**. Local spacing is calculated from the straight-line distances to adjacent original points, so this is not a fixed number of pixels.

For example, a local spacing of 50 pixels produces a shift of 2 pixels.

The same original pattern is tested with shifts in opposite directions. Original coordinates, target, rotation, reflection, and display scale remain matched. This lets researchers ask whether moving a particular fixed dot changes the participant's chosen position.

### 5. Mix the trial order

The default **identification block** identifies the influence of each fixed dot:

- 6 curve families × 2 hidden locations = 12 original patterns.
- Each pattern has 1 trial with no displaced dots.
- Each has 16 trials: 8 fixed dots × 2 displacement directions.
- Each has 4 trials that displace both neighbors of the hidden point.
- Total: **252 experimental trials**, with one repetition by default.

The paired shifts test whether two dots' effects approximately add together. Trials are shuffled using a recorded random seed. The default seed is fixed, so default runs are reproducible rather than newly randomized on every launch.

An optional **segmentation block** uses larger shifts: 8%, 16%, 32%, and 64% of local spacing. It asks whether a strongly displaced dot stops being treated as part of the same curve. Its default is 150 trials at the midpoint target. It records position settings, not a direct yes/no answer about whether a dot belongs to the curve.

## What is the scientific idea?

**Curvature** means how strongly a path bends. **Curvature variation** means how that bending changes as you move along the path. A circle bends equally everywhere; a polynomial generally does not.

The working idea is that people may use a common rule for making shapes look smooth, with different surrounding geometry producing different influences on their choices. Cubic and quintic stimuli can therefore look similar while still having different patterns of bending.

The current program collects responses to investigate this idea. It does not prove the hypothesis, fit an observer model, or calculate the final influence estimates automatically. Explicit circle-versus-polynomial curvature-matched pairs are not yet implemented. One repetition and one small shift size are starting points for a pilot, not a complete test of every hypothesis.

1. Open this project in PyCharm.
2. Select a Python interpreter with the packages in `requirements.txt` installed. The environment previously verified on this machine is `/Users/yangbolin/PyCharmMiscProject/.venv/bin/python`.
3. Open `run_exp.py` and click Run. No parameters are required.
4. Read the instructions, complete practice, and begin the experimental trials.

The default participant label is `pilot`. For a participant session, put this in the PyCharm Run Configuration's **Parameters** field:

```text
--participant-id P001 --session-id 1
```

To run the optional larger-displacement block:

```text
--block segmentation --participant-id P001 --session-id 2
```

## Where do the two CSVs go?

A CSV is a plain-text table that can be opened in a spreadsheet program or read by analysis software.

Normal runs create two files inside **`data/` next to `run_exp.py`**. The full paths appear in the PyCharm Run console. Filenames include the participant, block, session, and a timestamp, for example:

```text
P001_identification_s1_<timestamp>_trials.csv
P001_identification_s1_<timestamp>_presses.csv
```

Both files are created with headers before the welcome screen. Each submitted experimental trial adds one row to each file. Saving finishes before the next trial starts, and the console reports `Trial 1: both CSV files saved.` Practice and an unfinished trial are not recorded.

The timestamp prevents a normal new run from overwriting an earlier session. An explicit output prefix that already exists is rejected. If a spreadsheet viewer is already open, refresh or reopen the file to see newly saved rows.

`recorder.py` also has older default filenames, `pixel_based_adjustment_data.csv` and `button_press_sequence.csv`. **`run_exp.py` supplies the timestamped filenames above**, so the older files in the project root are not the current run's output.

### File 1: `..._trials.csv` — What was shown, and where did the person put the dot?

**Each row describes one completed experimental trial.** This is the main file for studying responses and their relationship to the stimulus.

| Important columns | What they mean / why they are useful |
|---|---|
| `participant_id`, `session_id` | Which participant and session the response belongs to |
| `trial`, `planned_order`, `trial_uid` | Trial number/order and the label used to match the two files |
| `stimulus_id` | Which original pattern was used; shared by its matched displacement conditions |
| `curve_family`, `curve_strength`, `target_index`, `num_points` | Shape, strength, hidden-point index, and total point count |
| `experiment_block`, `condition_type`, `repetition` | Experiment type; baseline, single-dot, or paired-dot condition; repeat number |
| `rotation_deg`, `reversed`, `sample_fractions`, seed columns | How the pattern was oriented, sampled, and generated |
| `perturb_indices`, `perturb_signs`, `perturb_fraction` | Which fixed dots were shifted, in which direction, and by what fraction of local spacing |
| `perturb_actual_units`, `perturb_actual_px` | Actual signed shifts in internal units and screen pixels; lists are used for paired shifts |
| `initial_offset_px`, `actual_initial_offset_px` | Requested and actual starting offsets; these may differ near a display boundary |
| `final_x_px`, `final_y_px` | Participant's submitted dot position on the screen |
| `correct_x_px`, `correct_y_px` | Original hidden point on the generating curve; a reference location, not proof of a perceptually correct answer |
| `response_normal_px`, `response_normal_units` | Signed distance of the submitted position from that reference along the movement line; the main response measure |
| `response_abs_px` | The same distance without its direction |
| `reaction_time_ms` | Time from trial-loop start to submission, in milliseconds; includes time spent adjusting |
| `total_moves` | Number of movement key events, not total distance traveled |
| `display_scale_px_per_unit` | Conversion from internal coordinates to screen pixels |

**How to read the response sign:** positive means toward the Z marker; negative means toward the / marker. Zero means the dot was placed at the original hidden location. A response of `+6` means 6 pixels toward Z from that location, not necessarily 6 pixels upward on screen.

Some columns are compatibility copies: `pixel_distance` and `pixel_distance_signed` repeat the signed pixel response; `pixel_distance_abs` repeats its absolute size; `px_per_unit` repeats the display scale. They are not additional independent measurements.

#### Coordinates and shape measurements

There are repeated columns for each point. For example, for point 2:

- `x2_baseline_math`, `y2_baseline_math`: original coordinates before displacement.
- `x2_math`, `y2_math`: coordinates after any experimental displacement.
- `x2_px`, `y2_px`: those coordinates transformed to screen pixels.

**For the hidden target, these point-coordinate columns retain the hidden reference position.** The participant's actual setting is in `final_x_px`, `final_y_px` and `player_final_local_x`, `player_final_local_y`.

“Math” or “local” units are internal shape coordinates, not centimeters. Screen coordinates begin at the upper-left; x increases to the right and y downward.

Additional columns describe bending (`kappa` means curvature), spacing, turning angles, and how much a displacement changes those quantities. They help researchers relate responses to geometry rather than just shape names. The `target_dkappa_ds_baseline` and `local_dkappa_ds_rms_baseline` columns describe how curvature changes along the original point sequence. Most shape measures are estimated from sampled dots; columns labeled `analytic` instead use the generating equation. Spacing-weighted curvature measures are not pure measures of curvature variation.

### File 2: `..._presses.csv` — How did the person adjust the dot?

**Each row also represents one completed trial**, not one keypress. Use this file to examine adjustment behavior, such as direction changes and step-size choices.

| Column | Meaning |
|---|---|
| `trial`, `trial_uid`, `stimulus_id` | Link to the corresponding row in the trial file |
| `press_1`, `press_2`, … | Recorded adjustment actions in order |
| `r_presses` | Legacy field for positions of reset actions; normally empty because the current task has no reset key |

An example sequence is:

```text
press_1 = up_0
press_2 = up_0
press_3 = down_1
press_4 = step_small_1
```

This means: move twice toward Z, reverse toward /, then select the fine step. The number after the action is the cumulative reversal count, **not the pixel distance, timestamp, or keypress number**.

`up` represents Z or Up arrow; `down` represents / or Down arrow. `step_small`, `step_medium`, and `step_big` represent keys 1, 2, and 3. The original physical key is not distinguished within each movement pair. Selecting a step size clears the direction memory used for detecting the next reversal, but does not erase the recorded cumulative count.

Trials with fewer actions have blank later `press_...` cells. Additional columns appear as longer sequences are recorded. This file does not contain individual action times, a continuous movement trace, or the final submission click/key.

### How should the two files be used together?

Within one run, match rows by `trial_uid` (and check `trial`). Across multiple runs, also keep the participant, session, and filename timestamp: trial labels can repeat between sessions.

- Use the **trial file** to ask how changing a fixed dot changes the participant's final setting.
- Use the **press file** to inspect how the participant reached that setting.
- Compare matched positive- and negative-shift trials to estimate a dot's influence. For example, if a +2-unit shift produces a +1-unit mean response and a −2-unit shift produces a −1-unit mean response, the estimated influence is `(1 − (−1)) / (2 − (−2)) = 0.5`. This is an illustration, not a measured result.

Completed rows are saved after every trial. Each file is replaced safely on its own, but the two replacements are not one indivisible operation; a disk failure between them can leave different row counts. Check matching trial IDs before analysis. Older sessions may also use eight total points instead of nine; do not silently combine them with the current design.
